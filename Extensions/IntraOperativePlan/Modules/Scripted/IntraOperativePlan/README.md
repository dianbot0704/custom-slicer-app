# Intra-Operative Plan – Page Authoring Guide

This module exposes a minimal page framework to help contributors implement wizard-like
flows. Every page inherits from one of the shared base classes defined in
`IntraOperativePlan.py`.

## Page types

| Class              | When to use it                                                                                     |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `DockWidgetPage`   | The page is just a traditional Slicer module widget and should stay inside the standard dock panel. |
| `CustomLayoutPage` | The page needs to take over the entire layout (e.g., surgical views, patient management consoles).  |

Both classes ultimately derive from `BasePage`, which loads the `.ui` file, wires the
navigation buttons, and exposes the `enter()` / `exit()` hooks.

### Common constructor arguments

All page classes share the same arguments:

```python
class ExamplePage(DockWidgetPage):
    def __init__(self, resourcePath, on_previous=None, on_next=None, parent=None):
        super().__init__(
            resourcePath=resourcePath,
            ui_filename="UI/example_page.ui",
            on_previous=on_previous,
            on_next=on_next,
            parent=parent,
        )
```

* `resourcePath`: passed by Slicer, use it to resolve `.ui` files.
* `ui_filename`: Qt Designer file to load.
* `on_previous` / `on_next`: callbacks supplied by `IntraOperativePlanWidget`; exposing
  navigation buttons is optional but recommended.

### Full-layout pages (`CustomLayoutPage`)

```python
class ImagingPage(CustomLayoutPage):
    def __init__(self, resourcePath, on_previous=None, on_next=None, parent=None):
        super().__init__(
            resourcePath=resourcePath,
            ui_filename="UI/imaging_page.ui",
            layout_id=PATIENT_MANAGEMENT_LAYOUT_ID + 2,
            tag_name="imaging_page",
            layout_description="""
                <layout type="vertical">
                    <item><imaging_page /></item>
                </layout>
            """,
            on_previous=on_previous,
            on_next=on_next,
            parent=parent,
        )
```

* `layout_id`: pick a unique integer (keep using the `PATIENT_MANAGEMENT_LAYOUT_ID + N`
  pattern).
* `tag_name`: custom XML tag used by the layout manager.
* `layout_description`: XML snippet that wraps the custom tag. When omitted, a simple
  horizontal layout is autogenerated.
* `enter()` / `exit()`: override these if the page needs additional setup while the
  layout is active (loading nodes, showing overlays, etc.). Always call
  `super().enter()` / `super().exit()` when you override them so the layout manager can
  register/restore the layout.

### Adding a page to the module

1. Implement the page class in `IntraOperativePlan.py` (or split it into another file if
   it grows large).
2. Instantiate the page inside `IntraOperativePlanWidget.setup()` right next to the
   other `self.page_*` definitions, remembering to pass `**nav_callbacks`.
3. Append the page to `self._pages` in the intended order.
4. If the page is dock-based, no extra wiring is required; the widget stack already
   hosts all dock pages. For full-layout pages, nothing else is needed—the base class
   handles registration and layout switching automatically.

### Navigation callbacks

* The framework wires buttons named `navPreviousButton` and `navNextButton` if they are
  present in the `.ui` file.
* You can still add custom buttons and manually call `self._on_next()` or
  `self._on_previous()` when needed.

### Checklist for new pages

1. Design the `.ui` file under `Resources/UI`.
2. Implement a page class deriving from the appropriate base.
3. Hook the page into `IntraOperativePlanWidget`.
4. (Optional) Override `enter()` / `exit()` for page-specific initialization/cleanup.
5. Run `python3 -m py_compile Extensions/IntraOperativePlan/Modules/Scripted/IntraOperativePlan/IntraOperativePlan.py`
   to ensure syntax correctness before committing.

Following this guide keeps page behavior consistent and guarantees the dock widget and
custom layouts are shown/hidden automatically when engineers add new steps to the
workflow.
